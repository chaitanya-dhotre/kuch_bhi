S1

The finding, why a recovery key, and what each option buys

  • Exactly 6 digits: six one-character controllers backup_pin_screen.dart:89-95; valid only when pin.length == 6 && isDigitsOnly :157-176.
  • PBKDF2-HMAC-SHA256 at 100,000 iterations: _isoPbkdf2 encryption_service.dart:151-163, called at :818-822 and :878-882.
  • Ciphertext + 32-byte salt on the users record: backupPrivateKey :801-852, fields at :846-847. Until 2026-10-30 any signed-in account could list them all (S10).
  • Also found: Change PIN "verifies" by restoring (backup_pin_screen.dart:195-197 → restorePrivateKey overwrites the device key, re-publishes the public key and wipes cached keys encryption_service.dart:897-934); no-backup reads as "Incorrect PIN" (:869-872); $e in user text backup_pin_screen.dart:312.

How WhatsApp and Signal get away with short PINs: the guess counter lives in tamper-resistant hardware (WhatsApp's HSM Backup Key Vault, Signal's SGX enclaves) that never hands out the encrypted key and locks after a few wrong tries. Their long codes (WhatsApp's 64-digit key, Signal's backup recovery key) are for when that box isn't trusted. PocketBase has no such box and the blob can be copied, so the secret itself must be unguessable. 125 bits is beyond any GPU farm; the X25519 key it protects is ~128-bit itself, so more bits would buy nothing. The real risks are where people keep it and losing it, which D2's copy and decision 11 address.

S4

Setup: the key step and the check step (C1–C7, D2, D3)

The key is made on the phone (25 × Random.secure().nextInt(32), Crockford alphabet without I, L, O, U) and lives only in the screen's state until saved. Copy → toast Recovery key copied. The check step takes the whole key, typed or pasted, any case, with or without dashes; autofill newPassword so a password manager offers to save it. Turn on backup enables only on a match; then the clipboard is cleared if it still holds the key. TalkBack reads the key character by character, groups separated. Start Fresh uses the same two steps (title Start fresh: save your new recovery key) and only then makes the new key pair.
S5

Restore at sign-in (D6, C6, E1)

One field takes the recovery key or the old 6-digit PIN (decision 8); the stored blob decides how the input is read. Visible by default (it's long), with a show/hide toggle. I lost it opens the Start Fresh dialog (S7). Below: wrong key (field kept so a typo can be fixed), a short key (caught before any server call), no backup.

The K1/K3 rule holds. This page never generates an X25519 key and never uploads a public key. The single writer re-reads the record and refuses when the server's public_key differs from the device key, so a re-wrap only ever replaces a blob with the same key under a new secret. Interrupted at any point: the server record is the only truth (one atomic PATCH); no local "in progress" flag.
S10

Server: what the live read found, the hook (live), the alternative migration

Confirmed live 2026-10-30 (read-only): worse than the audit says. users listRule and viewRule are both @request.auth.id != "", neither backup field was hidden, and no hook hid them. Any signed-in account could list all 5 users' backup blobs in one request. Rate limiting is on (PocketBase defaults) but cannot help: guessing happens offline. The H2 hook below went live on 2026-10-30 and was verified on a DB copy and on both phones; blobs copied before then stay crackable until their owner moves to a recovery key, and even then the old copy opens the same X25519 key.

R1–R3, read-only (done, approved):

H2, live since 2026-10-30: pb_hooks/key_backup_hide.pb.js, deployed by scp + sudo mv, backup /home/ubuntu/pb_backups/pb_hooks.20261030-key-backup-hide-pre. Rollback: delete the file, restart.

/// <reference path="../pb_data/types.d.ts" />
// Security §8.2: only the owner (or a superuser) sees their encrypted key backup.
onRecordEnrich((e) => {
  const auth = e.requestInfo ? e.requestInfo.auth : null
  if (!auth || (auth.id !== e.record.id && !auth.isSuperuser())) {
    e.record.hide("private_key_encrypted", "private_key_salt")
  }
  return e.next()
}, "users")

Verified on a throwaway DB copy (same binary, port 8099): A lists users → only A's own blob + salt; B's absent, public keys present; A reading B → absent; A reading A → present. Live: health 200, no 4xx/5xx after restart, both phones open Home with no backup banner. Not separately tested: a user record reached through expand (same enrich path).

H3, only if decision 3 = separate field: pb_migrations/<unix>_users_backup_version.js, same pattern as the 2026-10-29 avatar migration (backup data.db, scp, sudo mv, restart, check _migrations).

/// <reference path="../pb_data/types.d.ts" />
migrate((app) => {
  const users = app.findCollectionByNameOrId("users")
  users.fields.add(new NumberField({ name: "private_key_backup_version", onlyInt: true, min: 0, max: 99 }))
  app.save(users)
}, (app) => {
  const users = app.findCollectionByNameOrId("users")
  users.fields.removeByName("private_key_backup_version")
  app.save(users)
})

Rate limiting (decision 5): no new limits. One fetch is enough for an offline attack, and the app reads users records constantly.
